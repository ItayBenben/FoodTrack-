# Implementation notes

Decisions taken where the specs were silent or where the build environment forced a choice.
Each one is numbered so it can be referenced from code and from review. Any you disagree with
becomes a spec change, in the same commit as the code that follows it.

| # | Decision | Why |
|---|---|---|
| I-01 | **Hand-written SQL migrations with `.down.sql` files** (`apps/api/migrations`), applied behind an advisory lock by `src/db/migrate.ts`. No ORM generator; queries use `pg` with parameters only. | RLS policies, triggers, security-definer functions and matviews are not expressible in Drizzle Kit, and the analysis code needs raw SQL anyway. Spec `06` §1 names Drizzle; the deviation is deliberate. |
| I-02 | Two database roles: `foodtrack` (owner: migrations, reference-data seeding, matview refresh) and `foodtrack_app` (API, worker, analysis — every request-serving process). Neither is superuser; neither has `BYPASSRLS`. RLS is `ENABLE`d, not `FORCE`d. | `06` §5: the app role is never superuser and is not the owner, so every policy applies to it. `FORCE` was tried and removed: it makes the owner-run matview refresh read zero rows. The owner credential is used only by CLI/boot code, never on a request path. |
| I-03 | Pre-authentication lookups (login by email, single-user unlock, refresh-token lookup, passphrase reset) go through narrow `SECURITY DEFINER` functions (`auth_*`). | They must read a row before `app.user_id` is known. A definer function returns only the columns auth needs, so there is still no general cross-user read path. |
| I-04 | `uuidv7()` shim created only when `pg_catalog.uuidv7` is absent (PostgreSQL 16/17). Production pins PostgreSQL 18, which has it built in. | The dev/CI box here runs Postgres 16. |
| I-05 | Materialised views (`daily_exposure`, `food_tag_resolved`, `user_slot_time`) are **not** granted to the app role; it reads them only through `my_*` security-barrier views filtered by `app.user_id`. | Matviews cannot carry RLS policies. |
| I-06 | Sensitive *text field values* (e.g. `note.text`, `medication.name`, `meal.description`) live in `observation_value.value_enc` (bytea), selected by `"sensitive": true` in the tracker definition. | `06` §5.3 lists `observation.note`; a definition-driven app also needs a rule for free-text fields declared in config. The flag keeps it data-driven. |
| I-07 | `observation.def_hash` stores the content hash of the definition version the value was written under, alongside `def_version`. `tracker_definition_history` keeps every hash ever loaded. | `02` §2.3 requires observations to store the hash so incompatible versions are never pooled. |
| I-08 | Daily aggregation is **definition-driven** (`aggregation.daily` + `analysis` blocks), computed in TypeScript for the UI and in Python for the engine from the same definitions. The spec's hard-coded `daily_rollup` matview is replaced by this. | CLAUDE.md rule 1 forbids hard-coding trackers in analysis code; the `02` §4 matview names `stool` and `symptom` literally. |
| I-09 | Outcomes, confounders and covariates are declared on **aggregations** (`aggregation.daily[].analysis`), not only on fields. `notable_threshold` on a continuous outcome generates the binary `<key>_notable` companion of `04` §14.2. | A field (Bristol) yields several outcomes (`any_abnormal`, `loose`, `deviation`); the aggregation is the natural unit. |
| I-10 | Food component depth is measured across the **whole chain** (ancestors + descendants of the new edge) and capped at 3; cycles rejected by trigger. | `02` §12.1 rule 1. Checking only the new edge would let two depth-2 chains join into depth 4. |
| I-11 | Job queue is the `job` table with `FOR UPDATE SKIP LOCKED` claims (`job_claim`), not pg-boss. | One fewer dependency; `02` §3.5 already specifies the table. Durable across restarts, retries with backoff. |
| I-12 | Media is stored on a volume by default (`VolumeMediaStore`); MinIO is optional. Every object is encrypted with its own key, wrapped by the DEK. | `06` §1 names MinIO; D14 allows a plain volume. At one-box scale a volume is simpler to back up and restore. |
| I-13 | `change_log.payload` and `observation_revision.snapshot` hold narrative fields **sealed** (base64 ciphertext, AAD bound to the row). `/sync/pull` opens them and then passes the payload through the explicit column allowlist and `containsForbiddenKey`. | Otherwise the narrative layer would sit in plaintext in two audit tables. |
| I-14 | Model identifiers are not committed: `config/llm.json` names the env var that holds them (`ANTHROPIC_MODEL_TEXT`). With no key or no model set, the router falls through to `deterministic`. | Operators choose and update models without a code change. |
| I-15 | Seed foods (`config/foods/seed.json`, 131 foods with Hebrew + English names) carry approximate generic nutrient values so the app works with zero external APIs. The FDC / Tzameret ETL overwrites them when those datasets are present. | `06` §9 design rule: fully functional with no external food API. |
| I-16 | FODMAP classes are a self-authored, coarse table (`config/food-tags/fodmap.json`) mapping food groups → subgroup class. All citations are `needs_check` until a human verifies them. | D12. No Monash data, no gram quantities. |
| I-17 | Weekend = Friday + Saturday (Israel) for the weekday confounder. | Primary user locale. Should become a user setting. |
| I-18 | **Multiplicity: one Benjamini–Hochberg family per analysis run**, not one per (outcome, lag window) as `04` §7 says. Configurable via `analysis.json` `fdr_family`. | With ~30 per-(outcome, lag) families, a user with no real effect still gets a false discovery in almost every run (1 − 0.9³⁰ ≈ 96%). The null-data gate failed at 18/20 users; with a run-wide family it is ~1% (500 users). CLAUDE.md rule 4: the gate decides, the engine changes. |
| I-19 | **Window outcomes are anchored per exposure.** An exposed day's window starts at the first qualifying exposure; an *unexposed* day's window starts at that exposure's own typical time of day (median, 30-min grid). | Anchoring unexposed days anywhere else (e.g. the day's median meal) compares different hours of the day, and every food eaten at a habitual hour looks associated. This was the first null-gate failure. |
| I-20 | **Conservative p-values.** Continuous outcomes use max(Welch, Mann–Whitney) p; when lag-1 autocorrelation exceeds 0.2 the block bootstrap gives the interval and the p-value is max(parametric, bootstrap). | `04` §6.2 names the rank-based check as robustness; Welch alone is liberal on the discrete, zero-inflated scales used (urgency 0–4, \|Bristol − 4\|). The bootstrap must never make a claim *stronger* than the model that ignored correlation. |
| I-21 | **One insight card per exposure.** Its strongest outcome leads; other outcomes are listed under it; nested exposures covering ≥90% the same days (food ⊂ tag) fold into it as "same days as". | `04` §7: a real dairy effect must not appear as three discoveries. Grouping happens at display; every comparison stays in the BH family. |
| I-22 | **Window outcome semantics.** For `any`/`max`/`sum` aggregations an empty window counts as 0 only when the user recorded an outcome (or an all-clear) on a day the window touches; otherwise the day is missing. `mean` aggregations are missing when empty. | Absence of a logged bad stool is only evidence of a good one on a day the user was logging stools at all. |
| I-23 | **Engine runtime.** The analysis service reads Postgres as `foodtrack_app` with `app.user_id` set per transaction; the API's worker refreshes the matviews on a separate connection before calling it. | Refreshing inside the job's transaction held an exclusive matview lock and deadlocked the engine's own read. |
| I-24 | **The clinician PDF is a print-ready report** (`/report`) that the browser saves as PDF, not a server-rendered PDF. | Correct Hebrew RTL shaping without shipping fonts and a PDF engine in the API image; the content is exactly 01 U8 (numbers only, no AI narrative). |
| I-25 | **Trial power** (`04` §14.4) asks whether the design would reach P(RD > 0) ≥ the decision bar under a true shift of exactly the MIE, in ≥ 80% of simulations. | Asking for P(RD > MIE) under a shift of exactly MIE centres on 0.5 by construction — no design could ever pass. |
| I-26 | **Continuous trial posterior** uses 20%-trimmed means with Yuen's standard error and a Student-t posterior, inflated for AR(1) when \|ρ\| > 0.2, instead of an MCMC Student-t likelihood. | Robust to the single terrible day the spec worries about, closed-form, no PyMC dependency; verdict tests cover the outlier case. |
| I-27 | **Design D** = 7–14 day run-in elimination, then six 3-day challenge periods (randomised in pairs, sealed with the DEK) separated by 3-day washouts, then follow-up. The verdict maps periods to arms only server-side. | `04` §10.6 specifies the principles, not the schedule. |
| I-29 | **Photo reading happens when the photo is added, online only.** `parse-photo` stores the photo and returns the foods; an offline photo uploads later with the meal but is not analysed retroactively. The vision model is the text model unless `ANTHROPIC_MODEL_VISION` is set. Only meal photos go to the model, never stool/symptom data. | Inference after the meal is saved would rewrite items the user may already have edited. A photo added then abandoned (draft discarded) leaves an orphan media row — acceptable at this scale. |
| I-30 | **Continuous deployment** = GitHub Actions `deploy` (after `ci` succeeds on a push to `main`) → GitHub OIDC → role `foodtrack-github-deploy` → SSM Run Command on the one instance, pinned to the tested commit. No SSH keys or AWS access keys anywhere. | Anyone who can merge to `main` can run root commands on the VM; that is the point of CD here, and `main` is the owner's. |
| I-31 | **The trial report (D44, S137) is data + a print-ready page**, not a queued server-side PDF: `GET /trials/{id}/report` returns the frozen pre-registration (now including `power`), schedule, completed sequence, raw days, deviations, adverse events and verdict; `/report/trial` renders it and the browser saves the PDF. | Same reasons as I-24 (Hebrew RTL without a PDF engine in the image). Built from the trial row, never from current config, so an older trial is reported under the settings it ran with. |
| I-28 | Restore drill (`scripts/restore-drill.sh`) is the CI gate for verified restore; it uses only the printed recovery card. | `06` §5.4. |
